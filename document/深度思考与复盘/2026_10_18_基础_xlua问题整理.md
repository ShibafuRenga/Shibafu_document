## 已经写下来的结论

### 值：`TValue`

Lua 里的值不是各写各的结构，外面统一是 `TValue`：一个 `Value` 联合体，加一个 `int` 做类型标签。

`Value` 里能对上的字段：

- `GCObject *`：要被 GC 管的对象
- `void *`：userdata
- `int`：布尔也放在这里
- 整数
- 浮点（笔记里的 number）

由此直接得到两条：

- 整数和浮点在表示上是分开的，所以平时写 Lua 感觉不到，不代表虚拟机里是同一种存储。
- table 不是联合体里的另一种裸值。它是堆上的对象，`TValue` 通过 `GCObject *` 指向那块内存。类型标签里另有 table 这个类型。

### `GCObject` 头

需要 GC 的对象带头：`next`、类型、GC 标记。`next` 把对象串起来，标记位给标记清除用。

只到这里。回收从哪些根出发、分几步，还没看。

### table 的两段

table 拆成两块：

- 数组段：头指针，以及长度。笔记里认为这里记的是容量，不是「里面有多少个非 nil 元素」。元素个数没有单独的计数器。
- 哈希段：node 数组的头指针、最后一个可用位置（`lastfree`）、大小。大小用 2 的 n 次，存的是 n。n 从 0 起，对应大小 1。

node 是键值对。value 就是 `TValue`。key 是 `TKey`：联合体里一边像完整 `TValue`，另一边是「类型 + 值 + 一个 `Node *`」。这个 `next` 用来串哈希冲突。冲突时不是在节点外面再挂一条链表，而是在这块 node 数组里找另一个槽位放进去。

内存的申请和释放走 `luaM_*`。这些函数具体做什么，笔记里只猜测和 GC 有关，还没看。

### 插入、查询、删除、长度

插入：先判断这个下标落不落在数组段里。落在里面就写数组；否则走哈希段。

哈希冲突时的走法，笔记里是这样记的，但前后还没写顺，不能当成已经看懂：

- 先看这个槽位上旧 key 的哈希，对不对得上当前槽位。
- 对不上，新元素放进这个槽。
- 对得上，就用 `lastfree` 往前找空位。
- 另一种记法是：对不上时新元素占当前槽，旧元素再交给 `lastfree` 去找地方。

查询：数组段有就在数组段取；没有再去哈希段，沿着 `next` 对 key。

删除：没有把节点摘掉这种操作，只是把对应 key 的 value 设成 nil。`table.remove` 一类 API 和这句话怎么并存，还没对上。

长度（`#`）：没有「元素个数」字段。笔记里整理的分支是：

```
数组容量非 0 且不满：
    返回二分查找得到的边界
否则看哈希段：
    哈希是空的：
        返回数组容量
    哈希不是空的：
        到哈希段里找边界
```

数组段上的二分：中间是空的就看前半，中间有值就看后半。像 `(1, 2, nil, 4)` 这种，长度会停在 2。笔记里已经怀疑：数组容量、中间有洞、非顺序写入时，这个结果很容易和直觉不一致。算法流程写下来了，边界情况还没验证。

### xLua 目前拼出来的半条链路

层是分开的：Lua 虚拟机自己跑字节码；和虚拟机打交道的是 C API；C# 通过 `DllImport` 调这份 C API，自己并不直接碰虚拟机内部。

`transform.position` 这一侧，生成代码表面是：

- `_Register` 把属性名 `position` 登记到 `_getPosition`。
- 创建 Lua 环境时把 `_Register` 注册进去，不是每次访问都现注册。
- getter 从 `ObjectTranslatorPool` 里按 `RealStatePtr` 找 translator，再由 translator 找到那个 C# 对象，取出 `position`，`translator.Push` 回栈。
- 这些 C# 方法被放进元表的 `__index`。访问发生在元表这条路上，而不是 Lua 自己的 table 字段查找。

`transform` 在笔记里被写成 userdata，不是一张普通 table。userdata 长什么样、和 table 是什么关系，还没答。
